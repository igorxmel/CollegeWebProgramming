# Практическая работа №8. Создание REST API

Продолжение седьмой работы. Там маршруты только отдавали данные, здесь над тем же
ресурсом выполняется полный набор операций: получение списка, получение одной модели,
добавление, изменение и удаление. Плюс обработка ошибочных запросов и фильтрация по
категории.

Ресурс по-прежнему свой, из проекта «Dream Sneakers», а не товары из примера методички.
База данных здесь не подключается, модели лежат в массиве JavaScript и живут, пока
работает сервер.

## Описание решения

```
Solution/
    app.js          сервер и шесть обработчиков
    data.js         массив моделей
    package.json    зависимости и команда запуска
```

Модели те же шесть, что отдавал каталог седьмой работы, и те же, что лежат в таблице
`product` базы из четвёртой. Поля у объекта свои: `title`, `brand`, `category`, `price`.
В примере методички поля называются `name`, `price` и `category`, но она прямо просит
структуру своей предметной области.

## Как запустить

```bash
npm install
```

```bash
npm start
```

В консоли появится «Сервер запущен на http://localhost:3000». Останавливается через
Ctrl+C. Проверял на Node.js 24.14.0 и Express 5.3.0.

Открыть в браузере можно только GET-запросы: адресная строка умеет отправлять лишь их.
Для POST, PUT и DELETE нужен Postman, Thunder Client или любой другой инструмент, умеющий
задавать метод и тело запроса.

## Маршруты

| Метод | Адрес | Что делает | Коды |
| --- | --- | --- | --- |
| GET | `/sneakers` | список моделей | 200 |
| GET | `/sneakers?category=Беговые` | список с фильтром по категории | 200 |
| GET | `/sneakers/:id` | одна модель | 200, 404 |
| POST | `/sneakers` | добавление | 201, 400 |
| PUT | `/sneakers/:id` | изменение | 200, 400, 404 |
| DELETE | `/sneakers/:id` | удаление | 200, 404 |

Фильтр по категории это дополнительное задание. Категории совпадают с теми, что в базе
четвёртой работы: беговые, повседневные, баскетбольные.

Тело для POST и PUT:

```json
{
    "title": "Nike Pegasus Trail 5",
    "brand": "Nike",
    "category": "Беговые",
    "price": 16990
}
```

## Разбор кода

`app.use(express.json())` подключает промежуточный обработчик, который читает тело запроса
и разбирает его как JSON. Без него `req.body` остаётся пустым, и ни POST, ни PUT работать
не будут.

Поиск модели вынесен в отдельную функцию, потому что нужен в четырёх обработчиках из
шести:

```js
function findById(rawId) {
    const id = Number(rawId);
    return sneakers.find((item) => item.id === id);
}
```

Приведение к числу обязательно: часть адреса приходит строкой, а `id` в массиве число, и
строгое сравнение `"1" === 1` даёт ложь, так что без него не нашлась бы ни одна модель.

Фильтр читается из строки запроса через `req.query`. Если параметра нет, отдаётся весь
список, иначе отфильтрованный:

```js
const { category } = req.query;
if (!category) {
    return res.status(200).json(sneakers);
}
```

Сравнение идёт в нижнем регистре, чтобы `?category=беговые` и `?category=Беговые` давали
одно и то же. Пустой результат это не ошибка: категория существовать может, просто моделей
в ней сейчас нет, поэтому отдаётся 200 и пустой массив, а не 404.

Идентификатор новой модели берётся из отдельного счётчика, а не из длины массива. Длина
уменьшается при удалении, и новая модель получила бы уже занятый номер, после чего
`GET /sneakers/:id` находил бы первую попавшуюся из двух. В примере методички
идентификатор берётся из `Date.now()`, что этой проблемы тоже не имеет, но даёт
четырнадцатизначные числа, с которыми неудобно проверять запросы руками.

Удаление сделано через `splice`, а не через `filter`:

```js
sneakers.splice(sneakers.indexOf(sneaker), 1);
```

`filter` вернул бы новый массив, и присваивание поменяло бы только локальную переменную в
`app.js`. Массив, на который ссылается `data.js`, остался бы прежним, и удалённая модель
вернулась бы при следующем обращении. В методичке массив объявлен прямо в файле сервера
через `let`, поэтому там `filter` работает, а при вынесенных в отдельный модуль данных уже
нет.

Проверка полей в POST и PUT одинаковая: если хоть одного не хватает, возвращается 400 и
сообщение. В методичке такая проверка есть только в POST, но изменение без неё затирает
поля модели значением `undefined`, так что она стоит в обоих обработчиках.

## Проверка запросов

Postman не ставил, запросы отправлял из браузера методом `fetch`: это те же HTTP-запросы
с теми же методами, заголовками и телом.

| Запрос | Код | Ответ |
| --- | --- | --- |
| `GET /sneakers` | 200 | шесть моделей |
| `GET /sneakers/1` | 200 | Nike Air Zoom Pegasus 40 |
| `GET /sneakers/999` | 404 | «Модель не найдена» |
| `POST /sneakers` с полным телом | 201 | новая модель с `id` 7 |
| `POST /sneakers` без цены и категории | 400 | «Необходимо заполнить все поля» |
| `PUT /sneakers/1` | 200 | модель с новым названием и ценой |
| `PUT /sneakers/999` | 404 | «Модель не найдена» |
| `DELETE /sneakers/3` | 200 | «Модель успешно удалена» |
| `DELETE /sneakers/3` повторно | 404 | «Модель не найдена» |

Фильтр проверял отдельно: `?category=Беговые` и `?category=беговые` дают одинаковые
четыре модели, `?category=Повседневные` одну, несуществующая категория пустой массив с
кодом 200, а запрос без параметра весь список.

После удаления модели с `id` 3 и добавления новой список содержит идентификаторы
1, 2, 4, 5, 6, 7, повторов нет.

## Теоретическая часть

**API** это набор правил, по которым программы обмениваются данными. В веб-приложении
цепочка выглядит так: интерфейс отправляет запрос к API, сервер его обрабатывает,
обращается к данным и возвращает ответ.

**REST** это архитектурный подход, в котором данные рассматриваются как ресурсы. У каждого
ресурса свой адрес, а что именно с ним делают, определяет HTTP-метод. Поэтому `/sneakers`
один и тот же адрес и для получения списка, и для добавления модели: различает их метод.

**Методы** соответствуют четырём операциям CRUD: GET это чтение, POST создание, PUT
изменение, DELETE удаление.

**Параметр маршрута** объявляется в пути через двоеточие (`/sneakers/:id`) и читается из
`req.params`. Он указывает, с каким именно объектом работать, и всегда приходит строкой.

**Строка запроса** это то, что идёт после вопросительного знака, читается из `req.query`.
Параметры там необязательные и обычно уточняют выборку: фильтр, сортировка, поиск.

**Тело запроса** передаётся при POST и PUT, содержит сами данные объекта и читается из
`req.body`, но только если подключён `express.json()`.

**Коды состояния** сообщают результат: 200 успешно, 201 объект создан, 400 в запросе
неполные или неверные данные, 404 объект не найден, 500 ошибка на стороне сервера.

## Ответы на вопросы

**1. Что такое API?**

Набор правил, по которым одна программа обращается к другой за данными или действиями.
Он скрывает внутреннее устройство: клиенту достаточно знать адрес, метод и формат данных.

**2. Что такое REST API?**

API, построенный по архитектуре REST: данные представлены ресурсами, у каждого ресурса
свой адрес, а действие над ним задаётся HTTP-методом. Ответы обычно в JSON.

**3. Чем REST API отличается от обычного маршрута Express.js?**

Маршрут это механизм, REST это соглашение о том, как эти маршруты устроены. Обычный
маршрут может называться как угодно и возвращать что угодно, например HTML-страницу.
В REST адрес называет ресурс существительным во множественном числе, действие выражается
методом, а не словом в адресе, и ответ приходит данными, а не разметкой.

**4. Для чего используется метод GET?**

Для получения данных. Он ничего не изменяет на сервере, поэтому повторный такой же запрос
даёт тот же результат.

**5. Для чего используется метод POST?**

Для создания нового объекта. Данные передаются в теле запроса, в ответ приходит созданный
объект и код 201.

**6. Для чего используется метод PUT?**

Для изменения существующего объекта. В адресе указывается идентификатор, в теле новые
значения полей.

**7. Для чего используется метод DELETE?**

Для удаления объекта по идентификатору из адреса. Тела у запроса нет.

**8. Что такое CRUD?**

Четыре базовые операции над данными: создание, чтение, изменение и удаление. В REST им
соответствуют POST, GET, PUT и DELETE.

**9. Для чего используется req.params?**

Чтобы прочитать параметр из самого пути, объявленный через двоеточие. В `/sneakers/3`
значение `3` попадёт в `req.params.id`. Приходит оно строкой, поэтому перед сравнением с
числовым полем его приводят к числу.

**10. Для чего используется req.body?**

Чтобы прочитать данные, переданные в теле запроса. Используется в POST и PUT, где нужно
передать сам объект, а не только его идентификатор.

**11. Зачем необходим express.json()?**

Это промежуточный обработчик, который читает тело запроса и разбирает его из JSON в объект
JavaScript. Без него `req.body` остаётся пустым, и сервер не увидит переданных данных.

**12. Что означает HTTP-код 200?**

Запрос выполнен успешно. Возвращается при получении данных, успешном изменении и
удалении.

**13. Что означает HTTP-код 201?**

Создан новый объект. Это точнее, чем 200: по коду ответа клиент понимает, что запись
действительно появилась.

**14. В каких случаях используется код 400?**

Когда запрос составлен неверно: не хватает обязательных полей, данные не того типа или
не проходят проверку. Здесь он возвращается, если в теле POST или PUT заполнены не все
поля.

**15. В каких случаях используется код 404?**

Когда запрашиваемого объекта не существует. Здесь это обращение к модели по
идентификатору, которого нет в массиве.

**16. Зачем использовать Postman или Thunder Client при разработке API?**

Они позволяют задать метод, заголовки и тело запроса и посмотреть ответ вместе с кодом
состояния. Без такого инструмента проверить POST, PUT и DELETE вручную не получится.

**17. Почему обычного браузера недостаточно для полноценного тестирования REST API?**

Адресная строка отправляет только GET-запросы и не умеет передавать тело. Проверить так
можно лишь получение данных, а остальные три операции остаются непроверенными.

**18. Где хранятся данные в данной практической работе?**

В обычном массиве JavaScript в памяти процесса, в модуле `data.js`. При перезапуске
сервера модуль выполняется заново, и список возвращается к исходным шести моделям.

**19. Что изменится после подключения MySQL?**

Данные переживут перезапуск и станут общими для всех экземпляров сервера. Обработчики
вместо работы с массивом будут отправлять SQL-запросы, а операции станут асинхронными,
потому что обращение к базе требует ожидания ответа.
