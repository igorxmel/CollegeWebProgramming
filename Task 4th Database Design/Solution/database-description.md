# База данных интернет-магазина Dream Sneakers

Предметная область та же, что и в первой практической работе: магазин кроссовок с каталогом,
корзиной, заказами и отзывами покупателей. База должна хранить модели обуви с брендами и
категориями, остатки по размерам, покупателей, их заказы с позициями и отзывы на товары.

## Описание таблиц

### brand

Бренды, под которыми выпускаются модели. Вынесен в отдельную таблицу, чтобы название и
страна бренда хранились один раз, а не повторялись в каждой карточке товара.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `brand_id` | целое | PK | Идентификатор бренда |
| `name` | строка (80) | | Название бренда, уникальное |
| `country` | строка (60) | | Страна бренда |

### category

Категории каталога: беговые, баскетбольные, повседневные и так далее.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `category_id` | целое | PK | Идентификатор категории |
| `name` | строка (80) | | Название категории, уникальное |

### product

Модель кроссовок. Одна запись это одна модель без учёта размера.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `product_id` | целое | PK | Идентификатор модели |
| `brand_id` | целое | FK → `brand.brand_id` | Бренд модели |
| `category_id` | целое | FK → `category.category_id` | Категория каталога |
| `name` | строка (120) | | Название модели |
| `description` | текст | | Описание для карточки товара |
| `price` | десятичное (10,2) | | Текущая цена в рублях |
| `is_active` | логическое | | Показывать ли модель в каталоге |
| `created_at` | дата и время | | Дата добавления в каталог |

### size

Справочник размеров. Хранит соответствие европейской и американской шкал, поэтому таблица
заполняется один раз и переиспользуется для всех моделей.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `size_id` | целое | PK | Идентификатор размера |
| `eu_size` | десятичное (4,1) | | Размер по европейской шкале |
| `us_size` | десятичное (4,1) | | Размер по американской шкале |

### product_size

Связующая таблица между моделями и размерами. Реализует связь «многие ко многим»: одна
модель выпускается в нескольких размерах, один размер встречается у множества моделей. У
связи есть собственный атрибут, остаток на складе, поэтому таблица не могла быть заменена
парой внешних ключей в других таблицах.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `product_size_id` | целое | PK | Идентификатор пары «модель и размер» |
| `product_id` | целое | FK → `product.product_id` | Модель |
| `size_id` | целое | FK → `size.size_id` | Размер |
| `stock_quantity` | целое | | Остаток на складе в парах |

Пара значений `product_id` и `size_id` уникальна: одна модель одного размера не может
встречаться в таблице дважды.

### customer

Покупатели магазина.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `customer_id` | целое | PK | Идентификатор покупателя |
| `first_name` | строка (60) | | Имя |
| `last_name` | строка (60) | | Фамилия |
| `email` | строка (120) | | Почта, уникальная |
| `phone` | строка (20) | | Телефон |
| `created_at` | дата и время | | Дата регистрации |

Имя и фамилия хранятся раздельно: единое поле «ФИО» нарушало бы первую нормальную форму,
потому что содержало бы несколько значений в одной ячейке.

### customer_order

Заказ покупателя. Таблица названа `customer_order`, а не `order`, потому что `ORDER` это
зарезервированное слово SQL и его пришлось бы постоянно экранировать кавычками.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `order_id` | целое | PK | Номер заказа |
| `customer_id` | целое | FK → `customer.customer_id` | Покупатель |
| `status` | строка (20) | | Состояние заказа: новый, оплачен, отправлен, доставлен, отменён |
| `delivery_address` | строка (200) | | Адрес доставки на момент оформления |
| `created_at` | дата и время | | Дата оформления |

Суммы заказа в таблице нет: она вычисляется по позициям заказа. Хранить её отдельно значило
бы держать вычисляемое значение, которое рассинхронизируется при любом изменении позиций.

### order_item

Позиция заказа. Связующая таблица между заказом и конкретной парой «модель и размер».

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `order_item_id` | целое | PK | Идентификатор позиции |
| `order_id` | целое | FK → `customer_order.order_id` | Заказ |
| `product_size_id` | целое | FK → `product_size.product_size_id` | Модель нужного размера |
| `quantity` | целое | | Количество пар |
| `unit_price` | десятичное (10,2) | | Цена за пару на момент оформления |

Поле `unit_price` дублирует `product.price` только на первый взгляд. Цена в каталоге со
временем меняется, а в заказе должна остаться та, по которой покупатель фактически купил
товар. Это не избыточность, а самостоятельный факт, привязанный к моменту покупки.

### review

Отзыв покупателя о модели.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `review_id` | целое | PK | Идентификатор отзыва |
| `product_id` | целое | FK → `product.product_id` | Модель, о которой отзыв |
| `customer_id` | целое | FK → `customer.customer_id` | Автор отзыва |
| `rating` | целое | | Оценка от 1 до 5 |
| `comment` | текст | | Текст отзыва |
| `created_at` | дата и время | | Дата публикации |

## Логическая структура

Связи между таблицами:

1. `brand` → `product`, один ко многим. Один бренд выпускает много моделей, каждая модель
   принадлежит ровно одному бренду. Внешний ключ `product.brand_id`.
2. `category` → `product`, один ко многим. В одной категории каталога много моделей, модель
   относится к одной категории. Внешний ключ `product.category_id`.
3. `product` → `product_size`, один ко многим. Модель выпускается в нескольких размерах.
   Внешний ключ `product_size.product_id`.
4. `size` → `product_size`, один ко многим. Один размер встречается у множества моделей.
   Внешний ключ `product_size.size_id`.
5. `customer` → `customer_order`, один ко многим. Покупатель оформляет много заказов, заказ
   принадлежит одному покупателю. Внешний ключ `customer_order.customer_id`.
6. `customer_order` → `order_item`, один ко многим. Заказ состоит из нескольких позиций.
   Внешний ключ `order_item.order_id`.
7. `product_size` → `order_item`, один ко многим. Одна и та же пара «модель и размер»
   попадает в позиции разных заказов. Внешний ключ `order_item.product_size_id`.
8. `product` → `review`, один ко многим. У модели много отзывов. Внешний ключ
   `review.product_id`.
9. `customer` → `review`, один ко многим. Покупатель оставляет отзывы на разные модели.
   Внешний ключ `review.customer_id`.

Связи «многие ко многим» в схеме две, обе разложены через промежуточные таблицы:

- «модель и размер» через `product_size`, у связи есть атрибут `stock_quantity`;
- «заказ и товар» через `order_item`, у связи есть атрибуты `quantity` и `unit_price`.

## Нормализация

**Первая нормальная форма.** Все поля атомарны, повторяющихся групп нет. Имя и фамилия
покупателя разделены, размеры модели вынесены в отдельные записи `product_size`, а не в
строку вида «40, 41, 42», позиции заказа хранятся отдельными записями, а не списком в одном
поле.

**Вторая нормальная форма.** Первичные ключи всех таблиц простые, состоят из одного поля,
поэтому частичной зависимости неключевых полей от части ключа не возникает. В связующих
таблицах `product_size` и `order_item` неключевые поля зависят от всего ключа: остаток на
складе относится к конкретной паре «модель и размер», количество и цена к конкретной позиции
заказа.

**Третья нормальная форма.** Транзитивных зависимостей нет. Название и страна бренда лежат в
`brand`, а не в `product`, иначе они зависели бы от модели через бренд. Название категории
хранится в `category`. Данные покупателя лежат в `customer`, а не дублируются в каждом
заказе. Вычисляемая сумма заказа не хранится, а считается по позициям.

Единственное сознательное отступление это `order_item.unit_price`. Формально цена уже есть в
`product`, но там лежит текущая цена каталога, а в позиции заказа зафиксирована цена сделки.
Это разные по смыслу величины, поэтому нормальные формы здесь не нарушаются.
